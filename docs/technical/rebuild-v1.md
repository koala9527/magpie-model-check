> 文档版本：1.0\
> 项目名称：`magpie-model-check`\
> 项目定位：Magpie 插件形态的模型身份行为检测工具\
> 核心目标：检测 Magpie
> 中配置的模型，实际响应行为是否与用户声明的模型身份一致\

## 官方 Magpie 插件能力核验（重要，优先级高于下文通用架构建议）

本节根据当前官方文档核验，若下文其他章节与本节冲突，以本节和官方文档为准。

官方插件指南：<https://usemagpie.ai/docs/zh/plugins>

当前 Magpie 的社区插件并不是一个可以任意调用所有内部 API
的通用后台插件。官方文档区分了不同运行位置和能力：

1.  **Provider/OpenCode 插件**：在共享 Bun
    插件宿主中运行，官方列出的主要钩子包括
    `config`、`auth`（`loader`、`usage`、`refresh`、`checkin`）、`provider.models`
    和 `chat.headers`。Magpie 不会调用普通 OpenCode 插件的所有钩子。
2.  **Gateway middleware**：通过 `package.json` 的 `magpie.middleware`
    或 `*.middleware.js` / `*.middleware.mjs` 声明，在网关进程内由
    `moejs` 运行。可用钩子包括
    `onRequest`、`onAccount`、`onProvider`、`onEvent`、`onResponse`；`onProvider`
    能看到路由后的 Provider 信息（如
    `ctx.provider.id`、`ctx.provider.model`），`onResponse`
    能看到非流式完整响应，流式响应可观察事件。
3.  **Middleware 运行限制**：没有 `fetch`、定时器或 Node
    API；钩子有严格执行时限，异常或超时按 fail-open 处理。不能把它当作
    Go/Bun 常驻后台。
4.  **`onUsage`**：能拿到用量记录，但不包含请求体、提示词或响应内容，不能单独用于
    ModelTrace 数字指纹采样。
5.  **插件页面**：运行在沙盒 iframe 中，没有 `fetch`、WebSocket
    或任意网络访问；只能通过官方 bridge
    和声明权限读取有限数据。`providers:list` 只提供 Provider ID
    和名称，不提供 API Key、账号密钥或请求内容。
6.  **MCP
    工具**：社区插件可以提供工具，工具在插件宿主中执行，官方示例允许在
    `execute` 中使用
    `fetch`，并有执行时限。它适合承载用户主动触发的检测动作，但不能假设它能自动读取现有
    Provider 的密钥或凭据。

以上限制意味着：**仅靠 Gateway middleware 无法在后台主动向某个已有
Provider 发起额外探针请求，也不能直接把完整原始样本写入数据库。**
`onProvider` / `onResponse` 更适合观察实际业务请求；MCP
工具更适合显式触发主动检测。二者的通信、持久化和探针路由关联必须通过 PoC
验证，不能凭空假设。

### 必须先做的插件能力 PoC

在正式重构前，先创建最小插件并验证：

-   是否能以一个社区插件包同时声明 Gateway middleware、MCP tool 和
    plugin page；
-   `onProvider` 是否能可靠看到目标请求最终命中的 Provider 和 model；
-   `onResponse` / `onEvent` 是否能关联同一次请求；
-   MCP tool 是否能向本机 Magpie Gateway 发起请求；
-   用户能否以官方支持的方式为该工具配置 Gateway URL / Gateway key；
-   MCP tool 发出的探针是否会经过同一条路由规则；
-   能否为探针设置唯一标记，并由 middleware 可靠识别和关联；
-   是否存在官方支持的持久化或 sidecar 通信方式；
-   插件关闭或重载时任务、监听器和资源是否正确释放。

PoC 结果必须记录在 `docs/magpie-api-audit.md`。未验证的能力一律标记
`待验证`。

### 推荐的真实可行架构

优先采用**社区插件包 + Gateway middleware + MCP tool + 插件页面**：

-   Gateway middleware：观察真实业务请求的 `onProvider` 和 `onResponse`
    /
    `onEvent`，只做轻量、限时的观测或请求标记；不在请求热路径中执行长时间指纹计算。
-   MCP tool：由用户主动调用，触发一次或多次身份探针；优先通过 Magpie
    本机 Gateway 请求目标模型。
-   Plugin page：展示目标配置、检测结果和历史；只使用官方
    bridge、options 和权限允许的读取能力，不能直接 fetch 本地服务。
-   持久化：先确认插件宿主支持的安全持久化方式。若必须使用
    sidecar，必须明确 sidecar
    的安装、启动、停止、IPC、认证和跨平台打包方案；不得假设 middleware
    能启动 Go 服务或访问文件系统。
-   Go 检测引擎：仅在确实需要且已验证可用的 IPC / sidecar
    生命周期后引入。V1 不应为了沿用旧项目而强行保留 Go 后台。

### 两种检测模式必须分开标记

**A. Active Probe（主动探针）**

由用户通过 MCP 工具或插件界面触发，向 Magpie Gateway
发起专门的挑战请求。只有当请求被证明命中目标 Provider / route
时，才允许给出该渠道的身份归因结论。若无法关联实际路由，结果必须为
`ROUTE_UNVERIFIED`。

**B. Passive Observation（被动观测）**

从真实业务请求的 `onProvider` / `onResponse` / `onEvent`
观察模型行为。默认不保存用户提示词和完整业务响应；只有用户显式开启并知情同意，才可保存必要的探针样本。普通业务内容不能未经同意混入官方指纹基准库。

被动观测到的样本不能自动视为标准挑战样本；只有响应确实来自受控、版本化挑战时，才可用于
ModelTrace 对照。

# 1. 项目目标与范围

## 1.1 核心问题

用户在 Magpie 中配置了一个模型，例如
`provider-a/gpt-x`，但上游渠道可能：

-   将请求转发给同系列旧版本；
-   将请求转发给同家族的低规格模型；
-   将请求转发给其他模型家族；
-   根据负载、成本或策略动态切换模型；
-   在不改变对外模型 ID 的情况下更新底层模型。

本项目通过主动挑战采集响应行为指纹，并与可信参考基准进行比较，输出：

-   是否与声明模型的已知行为相符；
-   是否更接近另一个已知模型；
-   是否属于当前基准库无法识别的未知模型；
-   当前证据是否不足以判断；
-   检测是否因网络、限流、解析或预算问题而不可用。

## 1.2 首要优先级

1.  身份归因准确度和低误报率。
2.  开放集未知模型拒识能力。
3.  可信基准数据质量与跨渠道泛化。
4.  探针与实际业务请求路由一致性。
5.  数据可追溯、可复现实验。
6.  Magpie 插件集成稳定性。
7.  界面与便利性。

## 1.3 V1 范围

必须实现：

-   Magpie 插件集成，遵循官方插件开发指南；
-   从 Magpie 可用的官方插件接口获取必要模型/Provider
    信息；若官方接口不提供，则设计明确的用户配置流程；
-   用户选择目标模型并声明预期身份；
-   通过已验证的 Magpie 路由路径执行探针；
-   指纹挑战、原始样本保存和特征提取；
-   基准库导入、版本管理和来源标记；
-   已知模型归因与未知模型拒识；
-   历史记录和可解释报告；
-   手动检测优先，可配置定时检测；
-   本地存储和密钥保护。

V1 明确不做：

-   自动封锁、自动降级或自动切换 Provider；
-   云端 SaaS、账号体系和远程控制台；
-   与身份识别无直接关系的通用模型跑分；
-   以模型回答风格或"你是什么模型"作为主要身份判断；
-   未经验证的自动路由修改；
-   将检测结果作为法律或供应商违约的唯一证据。

# 3. 产品与技术架构

## 3.1 推荐逻辑架构

``` text
Magpie 社区插件包
  |
  +-- Gateway middleware（moejs，受限运行时）
  |     +-- onProvider：观察路由后的 Provider / model
  |     +-- onResponse / onEvent：观察响应
  |     +-- 轻量关联标记；不做长任务、不直接 fetch
  |
  +-- MCP tool（插件宿主）
  |     +-- 用户主动触发检测
  |     +-- 发起 Magpie Gateway 探针请求（PoC 验证后）
  |     +-- 请求预算、取消和超时
  |
  +-- Plugin page（沙盒 iframe）
  |     +-- 目标模型配置
  |     +-- 检测报告与历史展示
  |     +-- 通过官方 bridge / options 交互
  |
  +-- Fingerprint Engine
  |     +-- 响应解析
  |     +-- 特征提取
  |     +-- 指纹相似度
  |
  +-- Reference Bank / Attribution Engine
  |     +-- 可信基准、开放集拒识、校准
  |
  +-- Persistence
        +-- 优先使用官方支持的插件存储
        +-- 如需 sidecar，先验证 IPC 和生命周期
```

## 3.2 核心路由原则

**探针必须尽可能经过 Magpie 中与目标业务请求相同的 Provider
选择、路由和上游配置。**

但必须区分两个概念：

-   `target_model_id`：用户在 Magpie 中选择的目标模型；
-   `actual_route_evidence`：本次探针实际命中的 Provider / route
    的可验证证据。

如果 Magpie 官方插件 API
无法获取实际命中路由，或者插件无法通过官方支持的方式发起指定目标的内部请求，则：

1.  不得声称探针已验证与业务请求同路由；
2.  不得绕过 Magpie 直接调用官方模型来替代目标渠道检测；
3.  将结果标记为 `ROUTE_UNVERIFIED` 或 `INCONCLUSIVE`；
4.  在报告中显示路由验证限制；
5.  先实现手动配置和可验证的最小路径，必要时向 Magpie 官方插件 API
    提交能力需求。

## 3.3 防递归机制

探针请求不得再次触发同一个身份检测流程。

先验证 Magpie 是否允许通过官方支持的 request metadata、header
或上下文标记识别插件发起的探针。若没有可靠机制，不得使用易冲突的模型名前缀假装解决递归问题。

如果 MCP tool 通过本机 Gateway 发起探针，必须通过真实集成测试验证：

-   探针不会递归触发；
-   探针不会意外改变 Provider / route；
-   探针响应能与 middleware 观察到的实际路由信息可靠关联。

## 3.4 推荐技术选型

优先遵循 Magpie
当前插件运行时，不要为了复用旧项目而假设存在任意后台能力。

-   插件层：OpenCode 插件包及 Magpie 官方支持的 middleware / tool / page
    扩展点；
-   指纹算法：审计并复用原项目所依赖的 ModelTrace；
-   V1 计算：优先评估在 MCP tool 的插件宿主中完成；
-   存储：先核验官方插件可用的持久化能力；SQLite 可能需要
    sidecar，不得假设 middleware 可直接访问；
-   Go 检测引擎：只有在 sidecar
    启停、IPC、权限和跨平台发行都验证后才引入；
-   UI：使用 Magpie plugin page 和官方 bridge；
-   通信：只使用官方支持或经过源码和集成测试验证的接口。

不要为了沿用原项目 Go 后台而强行保留它。也不要因为 middleware
在网关进程内运行，就假设它能 `fetch`、读写文件或启动子进程。

# 4. 模型身份检测方法

## 4.1 证据分级

系统应明确区分以下证据：

  --------------------------------------------------------------------------------------
  证据                    可信用途                               不可用于
  ----------------------- -------------------------------------- -----------------------
  用户声明模型 ID         确定预期身份                           证明真实身份

  API 响应 `model` 字段   辅助排查、记录元数据                   单独证明真实模型

  响应头、渠道自报信息    辅助诊断                               单独证明真实模型

  模型自我介绍            不作为身份依据                         身份认证

  行为统计指纹            概率性行为归因                         密码学身份认证

  官方签名身份声明        在验证签名、来源和有效期后作为强证据   未验证时直接信任

  可信执行证明            在证明链验证通过时作为强证据           未验证时直接信任
  --------------------------------------------------------------------------------------

产品主结论必须基于行为指纹及其验证数据；其他元数据只能作为辅助证据。

## 4.2 指纹算法迁移

如果原项目集成 ModelTrace：

1.  先固定上游仓库 URL、commit SHA 和许可证；
2.  阅读算法源码和训练/基准数据来源；
3.  记录原算法版本、特征维度、归一化方法和评分权重；
4.  建立原实现的 golden test；
5.  再决定直接调用、移植或封装；
6.  保留第三方许可证和版权声明。

不得只看 README 就宣称已完整复现算法。

## 4.3 数字序列挑战

如果现有算法使用数字生成挑战，先保持原挑战协议不变以便复现基线，再设计新版本实验。

挑战采集需要：

-   版本化 prompt；
-   固定请求参数；
-   固定输出格式；
-   明确最小/最大有效数字数量；
-   严格解析整数；
-   检查越界、重复格式、额外文本和截断；
-   保存原始响应；
-   保存解析结果；
-   对无效样本记录原因，不得静默丢弃。

每轮挑战数、数字长度、temperature、top_p
等参数必须从现有算法和实验验证出发确定，不得把未经验证的参数当作通用事实。

## 4.4 特征与评分

若原算法采用数字分布、Hellinger
距离、有序分块或其他统计特征，迁移时必须保留其原始数学定义和版本。

要求：

-   原始特征计算可独立单测；
-   特征维度、归一化和边界条件明确；
-   同一输入在原实现和新实现间进行数值对照；
-   原始距离与归一化相似度分开命名；
-   不将相似度称为概率；
-   不在没有训练/校准数据时解释 softmax 为真实身份概率。

先复现原算法，再做增强。不要同时修改算法、挑战提示词和参考数据，以免无法定位性能变化来源。

# 5. 基准指纹库与实验设计

## 5.1 基准来源

基准库必须记录来源，不得把不同来源混成一个"官方基准"。

建议来源类型：

-   `official_api_reference`：通过供应商官方 API、明确版本和模型 ID
    采集；
-   `magpie_provider_reference`：通过 Magpie 的指定 Provider 采集；
-   `third_party_channel`：第三方渠道样本；
-   `unknown_test`：用于开放集拒识测试的模型；
-   `manual_import`：人工导入，必须记录来源证明和审核状态。

"通过官方 API
采集"也不等于获得了密码学身份保证，只是相对可信的实验标签来源。

## 5.2 数据集拆分

每个模型的数据至少分成：

-   `train/reference`：建立模型指纹中心或分布；
-   `calibration`：校准距离阈值和置信度；
-   `test`：最终独立测试；
-   `unknown_test`：基准库之外的模型；
-   `channel_holdout`：未参与训练的渠道；
-   `time_holdout`：不同日期采集的数据。

按采集批次、会话、日期或渠道分组切分，避免相近样本泄漏到训练集和测试集。

## 5.3 交叉实验

必须至少研究：

1.  同一模型、不同渠道；
2.  同一模型、不同日期；
3.  同一模型、不同采样参数；
4.  同一家族、相邻版本；
5.  不同模型家族；
6.  基准库之外的未知模型；
7.  同一模型在不同系统提示词下；
8.  上游模型更新前后。

实验必须能回答：算法识别的是模型本身，还是渠道、系统提示词、采样参数或时间差异。

## 5.4 样本数量

先进行小规模可分性实验，再决定是否扩大采集。

建议流程：

-   探索阶段：每个模型采集若干独立批次，确认特征是否稳定；
-   校准阶段：扩大样本并建立独立校准集；
-   验证阶段：使用未参与建库的日期、渠道和批次；
-   发布阶段：报告样本量、置信区间和适用范围。

不要把"每模型 30、100 或 500
批"写成必然足够的标准。最终样本量应由目标误报率、置信区间宽度、模型间可分性和采样成本决定。

## 5.5 重点评估指标

必须输出：

-   Top-1 Accuracy；
-   Family Accuracy；
-   False Match Rate；
-   False Replacement Rate；
-   Unknown Recall；
-   Known-class Rejection Rate；
-   Calibration Error / Brier Score（适用时）；
-   不同渠道和日期下的性能；
-   相邻版本单独表现；
-   各指标置信区间。

身份检测应优先控制 False Match Rate。不能只报告总体准确率。

# 6. 开放集识别与最终判定

## 6.1 禁止纯闭集强制分类

系统不得无条件从已知候选模型中选一个作为最终身份。

必须允许：

-   未知模型；
-   证据不足；
-   模型家族可判断但版本不可判断；
-   路由不可验证；
-   请求不可用。

## 6.2 建议判定流程

``` text
收集有效挑战样本
       |
       v
检查样本质量和路由证据
       |
       +-- 路由不可验证 --> INCONCLUSIVE
       |
       +-- 样本不足/格式错误 --> INSUFFICIENT_EVIDENCE
       |
       v
提取指纹特征
       |
       v
与所有候选基准比较
       |
       v
检查类条件距离 / 候选间隔 / 跨挑战一致性
       |
       v
应用校准后的开放集拒识规则
       |
       +-- 与声明模型一致 --> MATCHED
       |
       +-- 稳定匹配其他已知模型 --> MISMATCHED
       |
       +-- 不属于已知分布 --> UNKNOWN
       |
       +-- 候选无法区分 --> INCONCLUSIVE
```

## 6.3 判定状态

  状态                 含义
  -------------------- ------------------------------------------------
  `MATCHED`            与声明模型的已验证行为基准相符
  `MISMATCHED`         稳定地更接近另一个已知模型，且证据达到校准标准
  `UNKNOWN`            与所有已知模型基准都不够接近
  `INCONCLUSIVE`       候选接近、跨挑战不一致或证据不足
  `ROUTE_UNVERIFIED`   无法证明探针走了目标 Provider / route
  `UNAVAILABLE`        超时、网络错误、限流、预算耗尽等
  `PENDING`            需要补充样本或复测

不要把 `UNKNOWN`、`UNAVAILABLE` 或 `ROUTE_UNVERIFIED` 自动转换成
`MISMATCHED`。

## 6.4 阈值校准

阈值必须从独立校准集产生。

建议比较：

-   类条件距离阈值；
-   候选间隔；
-   多挑战一致性；
-   开放集拒识方法；
-   conformal prediction（若数据条件和交换性假设适用）。

所有阈值都应随 `algorithm_version` 和 `bank_version` 版本化。

-   使用固定输入；
-   与原实现逐项对照；
-   检查特征维度；
-   检查距离；
-   检查排序；
-   检查数值误差；
-   保留 golden test 数据。

## 11.3 Magpie 集成测试

1.  插件可按官方方式安装、启用、禁用；

-   同模型同渠道；

-   跨家族模型；
-   基准库外模型；
-   不同日期；
-   不同采样参数；
-   不同系统提示词；
-   无效输出；
-   上游版本更新。

测试集必须与建库集和校准集隔离。

## 11.5 发布门槛

不要预先宣称固定准确率。

-   模型及版本范围；

-   训练、校准、测试样本数；
-   跨渠道表现；
-   相邻版本表现；
-   未知模型拒识率；
-   错误匹配率及置信区间；
-   已知限制。

# 13. 推荐实施顺序与停止条件

  -----------------------------------------------------------------------------------------------
  阶段                    核心问题                         停止条件
  ----------------------- -------------------------------- --------------------------------------
  P0                      Magpie                           无法确认目标请求路径时暂停自动探针
                          是否提供足够的插件和路由能力？   

  P1                      能否安全精简和改名？             破坏原插件生命周期时回滚

  P2                      能否复现原指纹算法？             无法复现时先解决算法差异

  P3                      基准样本是否可信？               来源不清晰的样本不得进入正式基准

  P4                      指纹能否区分目标模型？           误报不可接受时不发布身份结论

  P5                      探针是否命中目标渠道？           路由无法验证时不得宣称渠道身份已验证

  P6                      插件能否稳定运行？               影响普通业务请求时不得发布

# 15. 产品最终定义

`magpie-model-check` 是一个运行在 Magpie 中的模型身份行为检测插件。

它通过主动挑战、统计指纹、可信基准和开放集拒识，判断某个 Magpie
模型渠道的实际响应行为是否与用户声明的模型身份相符。

它不承诺通过黑盒行为百分之百证明底层模型身份。

它最重要的产品原则是：

**有证据才判断，证据不足就拒绝判断；宁可漏报，也不要把未知模型错误认证成用户购买的模型。**
